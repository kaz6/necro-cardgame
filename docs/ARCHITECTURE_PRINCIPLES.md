## 各原則の中身

### シミュ/描画分離 ◎

engine.js は `(state, action) => newState` の純粋関数として書く。
DOM / window / document に触れず、Node 単体で実行できる。
view.js は engine の state を読んで描画するだけで、ルール判定を持たない。
view が engine に働きかける唯一の手段は action オブジェクトを渡すこと。

### 決定性 ◎

乱数は engine 内部の seeded RNG のみ。RNG の状態は state の一部として持つ。
`Math.random()` の使用は禁止。同一シードから同一 action 列を適用すれば
常に同一の結果に到達する。リプレイ・デバッグ・サーバ再現がこれに依存する。

### データ外部化 ◎

カードの数値・効果は `data/cards.json` に置く。
バランス調整が JSON の編集だけで完結する状態を保つ。

### チート耐性 〇

権威サーバ型を前提とする。クライアントが送るのは action だけで、
state はサーバが唯一持つ。各クライアントへは `filterStateFor(state, playerId)`
を通した視点別 state のみを返し、相手の手札とデッキの中身は必ず落とす。

〇 止まりの理由: 通信経路と権威サーバ本体が未実装であり、
現時点では設計上そうできる、という段階にとどまる。

### 認証 △

現時点では未実装で、ローカルモックには不要。
ただし**ランクマッチ・クロスセーブを実装する時点で必須**になる。
それまでは対応しないが、後付けが困難にならないよう playerId の扱いを
engine 側で固定しない。

---

## 前提となる設計判断

オンライン対戦は**権威サーバ型**で実装する。
隠し情報（手札・デッキ）を持つため、**ロックステップ／ロールバックは採用しない**。

→ 詳細と却下理由は `DECISION_LOG.md` を参照。
