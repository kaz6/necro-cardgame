## 冒頭に置く前提 — 正本の向き

向きは **「誰が書くか」** で決まる。**「Notion が正本」とだけ覚えないこと**（2026-08-01 にこの言い方は不正確と訂正されている）。

### ★本企画の差分：SESSION_STATE と CURRENT_SPEC は **Notion が正本**

**この企画は天使様（IGPJ_02）と同じ扱い。** 遠征ギルドログとは向きが逆なので、マスターの記述をそのまま当てないこと。

| 文書 | 正本 | repo 側 |
|---|---|---|
| CURRENT_SPEC | **Notion** | `docs/CURRENT_SPEC.md` は写し |
| SESSION_STATE | **Notion** | `docs/SESSION_STATE.md` は写し |
| DECISION_LOG | **Notion** | `docs/DECISION_LOG.md` は写し |
| 却下案索引 | **Notion** | `docs/REJECTED.md` は写し |

**理由：** 設計判断がチャット側（設計担当の Claude）で行われ、そのまま Notion に書かれている。
**実装はまだ設計に追従する側**であり、repo の `docs/` は写しである。

したがって本企画では：

- ⑤-b（SESSION_STATE 写しの全置換）を **行わない**
- ⑤-c（CURRENT_SPEC の全置換）を **行わない**
- どちらも `update_content` で、**自分が持つ節（実装状況・次にやることの実装分・判断待ち）だけを外科的に更新する**
- 停止時の7項目は **Notion の SESSION_STATE ページに直接書く**（全置換しない）

⚠️ **全置換すると、チャット側（設計担当の Claude）が書いた記述を消す。**

### ★本企画の差分：写し宣言の向きが逆（CG-003 で追加）

マスターは **repo 正本**を前提にしているため、「Notion 側の写しページの冒頭に生成物宣言を置く」形になっている。
**本企画は向きが逆。宣言は repo 側の `docs/` に置き、Notion には置かない。**

| | マスター（repo 正本） | ★本企画（Notion 正本） |
|---|---|---|
| 宣言を置く場所 | Notion の写しページ冒頭 | `docs/` の各ファイル冒頭 |
| 宣言の中身 | 「これは repo からの生成物」 | 「これは Notion からの写し」 |
| Notion 側 | 宣言あり | **宣言を書かない** |

宣言は次の3点を必ず含める（`docs/SESSION_STATE.md` 等の実物を参照）:

1. **転記日時**。**推測せず `TZ=Asia/Tokyo date` と `git log` で確認する**
2. **写しであって正本ではないこと。正本は Notion の該当ページ**（`CLAUDE.md` のID表から引いた**ページIDを併記**する）
3. **このファイルを直接編集しても Notion には戻らないこと**

★ **規定は「3点必須＋任意の注記1行」**（2026-08-11 裁定）。
3点に加えて、**そのファイル固有の注記を1行だけ足してよい**。3点を削ってはならない。
注記は1行に収めること（増やすと宣言ブロックが読み飛ばされる）。

現に `docs/CURRENT_SPEC.md` は、反転予定を告げる注記を1行持っている。**これは規定違反ではない。**

宣言を置く対象は4ファイル: `SESSION_STATE.md` / `CURRENT_SPEC.md` / `DECISION_LOG.md` / `REJECTED.md`。

★ **Notion 側にこの宣言を書かないこと。**（⑤-c の「生成物の宣言は付けない」と同じ理由）
★ **③・③-b で更新するとき、冒頭の宣言ブロックを消さないこと。** 転記し直したときは転記日時を更新する。

★ **CURRENT_SPEC の宣言は、repo 正本へ反転した時点で外す。**
下記「将来の向きの反転」で `docs/CURRENT_SPEC.md` が正本になったら、
「これは Notion からの写し」という宣言は事実と食い違うため、**宣言ブロックを削除し、
代わりに Notion 側のページへ「これは repo からの生成物」の宣言を置く**（マスターの向きに戻る）。
反転の判定は人が行うので、**この差し替えも勝手に実行しない。**

★ **`docs/CURRENT_SPEC.md` には「将来 repo 正本へ反転する予定」の注記1行を残す**（2026-08-11 裁定 A）。
理由：**セッション間で `/clear` する運用のため、この SKILL.md はセッション終了時にしか読まれない。**
反転のタイミングで CURRENT_SPEC を開いている人が、**その場で宣言に期限があることを知れる**必要がある。
**取りこぼしにくさを、形の統一より優先する。**
→ 他の3ファイルに同じ注記は要らない（反転予定があるのは CURRENT_SPEC だけ）。

### ★将来の向きの反転（注記・勝手に実行しないこと）

**CURRENT_SPEC は、engine が仕様の実体になった時点で repo 正本へ反転させる。**

現在は「人が決めたルールを Notion に書き、実装がそれに追従する」段階なので Notion が正本。
engine のコードが仕様そのものになり、`docs/CURRENT_SPEC.md` を実装から書き起こす段階に入ったら、
遠征ギルドログと同じく repo 正本へ反転する。

★ **反転の判定は人が行う。このスキルが勝手に反転しないこと。**
反転すべきだと思ったら、停止して提案するにとどめる。

★ **反転時にやること：`docs/CURRENT_SPEC.md` 冒頭の写し宣言を外す。**
反転後は repo が正本になるため「これは Notion からの写し」は嘘になる。宣言ブロックを削除し、
Notion 側のページに「これは repo からの生成物」の宣言を置く（上の「写し宣言の向きが逆」節を参照）。

# 停止条件

以下に当たったら、作業を止めてユーザーに判断を仰ぐ。勝手に決めて記録すると、誤った内容が正本に入る。

1. 今回の決定が Notion の既存記述と矛盾する
2. 今回の決定が却下案索引で既に却下済みの案に該当する
3. 設計判断かどうかの分類がつかない
4. Notion のどのページに書くべきか判断がつかない
5. コミット対象に意図しないファイルが含まれている
6. **検証の修正を 2 回試しても通らない**
7. **CURRENT_SPEC のローカルと Notion の片側しか当たらない**（③-b と ⑤-c はセット）
8. ★ **正本の向きを反転すべきだと判断したとき**（勝手に反転しない）

## 停止時に出力する形式（7項目・順序と数は変えない）

1. **見出し**：要裁定とタスク名
2. **ページIDと、書いた節の名前**
3. **論点**（1行）
4. **A の内容**（1行。推奨があればその旨）
5. **B の内容**（1行）
6. **トレードオフ**（A と B をそれぞれ一言）
7. **既に却下済みの案があればそれ。なければ「なし」**

★★ **規則**

- このブロックは**要約であって正本ではない**。正本はタスクページ
- **ブロックだけ読んで裁定できる粒度にする。「詳細はページ参照」で済ませない。** それをやるとチャット側がページを全文取得することになり、トークン消費が大きい
- 最後は **A/B の一問一答で答えられる形**まで畳む（ユーザーは移動中に音声で返答することがある）

## 停止時の書き込み先

停止ブロックは**画面に出すだけで終わらせない。** SESSION_STATE の「判断待ち」節にも同じ内容を書く。

★ **本企画は Notion が正本なので、Notion の SESSION_STATE ページに直接書く。**
ただし**全置換しない**。`update_content` で「判断待ち」節だけを外科的に追加する。

- 書き込む内容は**上の7項目そのまま**
- **日時**と、**どのタスクページの作業か**（ページ名とID）を添える
- 「判断待ち」節が無ければ新設する
- ★ **判断が済んだら、次のセッションでその節を消す。** 残すと「複数の文書が現行を名乗る」状態になる
- ★ **この取り決めは session-end に限らない。** 作業中に判断を仰いで停止するとき全般に適用する

# 完了時に出力する形式（5項目・順序と数は変えない）

セッションを終えるときも、タスクページに詳細を書いたうえで、**チャットにそのまま貼れる短いブロック**を最後に出す。

1. **見出し**：完了とタスク名
2. **ページIDと、書いた節の名前**
3. **やったこと**（3行以内）
4. ★**指示からはみ出した点・未対応**
5. **commit**

★★ **項目4を空にしない。なければ「なし」と書く。** 欄があれば、自発的な申告に頼らず構造的に出てくる。

★ **先頭に実施日時（JST）を1行出す。** 日付は推測せず `TZ=Asia/Tokyo date` で取り直す。チャット側は現在時刻を持たないため、報告の日時が時系列の基準になる。

このブロックを出したあと、**次のセッションで最初にやることを1行**で示して終わる。
